# ADR-0027: 索引分片交换、嵌套 .gitignore 与「忙不等于死」的探活

- 日期:2026-11-02
- 状态:Accepted(已落地)
- 关联:ADR-0020(发送侧在途字节窗口)、ADR-0021(接收侧断点续传)、ADR-0012(忽略规则过滤入向)

## 背景

2026-11 的一次真实故障:`~/shared/syncx` 与 `~/shared/MoonUI` 两个共享目录连续两天
改动不上行,UI 一直显示「传输中」,对端停在旧版本。两端的 daemon、网络、磁盘都正常,
任何一层日志里都没有报错。故障链条是三个各自独立的既有缺陷叠加起来的:

1. **只读共享根目录的 `.gitignore`。** `composeIgnoreLines` 读 `<folder>/.gitignore`,
   不读子目录里的。syncx 仓库是 monorepo,`rust/.gitignore`(`/target`)与
   `moonbit/.gitignore`(`_build/`、`.mooncakes/`)从来没被读到过。实测索引里
   **105,128** 条构建产物(rust/target 104,556 + moonbit/_build 572),活跃条目
   106,863 条,真实文件 1,735 个。这不是 syncx 仓库的特例:Rust、MoonBit、
   npm/yarn workspaces、Bazel 一类工程几乎都在子目录里写 `.gitignore`。
   注意这不只是「多扫了垃圾」——那些条目还进了版本向量、参与每一轮索引比对与回推,
   而且构建产物每轮都在变,永远收敛不了。

2. **索引只有一个帧,不可分。** 链路吞吐正常时,50.94MB 的整份索引至少要占用写缓冲
   十几秒到几十秒。

3. **20s 的探活把「忙」判成「死」。** ping/pong 与数据共用同一条 ws socket。发大索引
   期间写缓冲被占满,pong 排在几十 MB 之后;`startHeartbeat` 只看「上一轮 ping 有没有
   pong」,没 pong 就 `terminate()`。重连后从头再发一份索引,再被占满,再判死 ——
   每 25~30 秒循环一次,永远发不完。这条死循环是整个故障的**放大器**,它让前两个缺陷
   从「慢」变成「永远不动」。

另外两处同样来自这个形状的隐患:`MAX_MESSAGE_BYTES = 64MB` 已经被 50.94MB 用掉 80%,
目录再长一点就会超;超过上限的帧由 ws 静默丢弃(不是优雅的报错),表现为「对端收到了
一份缺尾的索引」,比崩溃更难查。

## 决策

### 1. 嵌套 `.gitignore` 在扫描期改写为根相对规则

`readNestedGitignoreLines` 从共享根做广度优先遍历,遇到每个子目录的 `.gitignore` 就
把其中的规则**改写**成以共享根为基准的模式,追加到规则表里;后续目录继续用累积规则
判定是否要进入。这样 `composeIgnoreLines` 的返回值仍是「一组扁平行」,扫描器、入向闸门
(`peer.onPeerIndex`)、`filterIndexedEntries`、空目录规则、控制面快照的 `ignoreLines`
**全部不需要改动** —— 它们在结构上仍然只看一份根级规则表。

改写规则(gitignore 语义 → 根相对):

| 子目录 `d` 里的一条 | 改写为 |
|---|---|
| `foo` | `d/**/foo` |
| `foo/` | `d/**/foo/` |
| `a/b` | `d/a/b` |
| `/a` | `d/a` |
| `**` | `d/**` |
| `!foo` | `!d/**/foo` |

顺序是**浅目录先、深目录后**,配合既有的「最后匹配者胜」,自然得到 git 的
「深层 `.gitignore` 覆盖浅层」。被忽略的目录直接不进入遍历 —— 与 git 一致,也顺带
省掉 `rust/target` 那十万个条目的目录枚举。

两条刻意的保守:

- **目录名含 `* ? [ ] \` 时不改写也不深入。** 匹配器的转义集合并不完备(没有 `\`
  反转义语义,`[` 会直接破坏字符类),把这样的名字拼进模式可能**过度**忽略别的文件。
  宁可少忽略一个怪名字目录,不可多忽略。判定见 `dirPathExpressible`。
- **被忽略目录里的 `.gitignore` 不读**(git 同样不读),避免已排除子树里的规则产生
  二次作用。

`.syncxignore` 仍在最后追加,因此它的负向规则照旧可以推翻嵌套 `.gitignore`。

### 2. `index-chunk1` 能力协商 + 按编码字节切片

握手能力表新增 `CAP_INDEX_CHUNK1`(`index-chunk1`)。只在**对端宣告**时切:未宣告的
旧版对端会把每一片都当成一次完整的 `full` 索引去规划,那会把一次同步变成 N 次。签名
只覆盖 X25519 DER 公钥,加一个能力串不影响与旧版对端的互操作。

切分单位是**编码后的字节**,不是条数:单条条目可以有 8000 个 CDC 块,按条数切挡不住
「一条巨大条目独占一片」(`encodeIndexChunks`)。每片的目标是
`INDEX_CHUNK_PLAIN_BYTES` = 8MiB 明文,文本信封对明文约 16/9 倍 → 约 14.2MB,
离 64MB 上限很远。**单片能装下时仍然走原来的整份发送** —— 小目录的行为与升级前
逐字节一致(测试钉住了这一点)。常量可用 `SYNCX_INDEX_CHUNK_BYTES` 覆盖,
供测试用 16KiB 驱动同一条路径。

帧上带 `seq`/`total`(可选字段;旧版对端不会看到,因为能力没宣告就不分片)。接收侧
`attachPeerMessages` 按目录维护 `chunkAssemblies`:

- 无 `seq`/`total` = 完整索引,直接交给规划器(并丢掉该目录任何未完成的一半);
- 声明畸形(`seq >= total`、负数、`total > MAX_INDEX_CHUNKS = 256`)整体丢弃,不掀翻
  连接;
- 新的 `seq === 0`,或 total 变了 → 丢弃旧的重新开始(重连/重发不会拼出重复条目);
- 重复片忽略;集齐后才**调用一次** `onPeerIndex`;
- 拼装明文总量超 `MAX_INDEX_ASSEMBLY_BYTES = 256MB` 视为异常,整轮丢弃。

### 3. 分片是「背景流量」,每帧前等写缓冲

`sendChunkedIndex` 逐帧投递,每帧前 `waitForBulkSpace()`:写缓冲高于
`BULK_LOW_WATER_BYTES = 4MB` 就等(100ms 轮询,单帧最长等 30s 后照发 —— 链路彻底
不动时宁可退回旧行为,不能卡死)。于是 ws 的 ping 永远只排在一帧(≈14MB)之后,而不是
整份索引之后。帧之间还 `await setTimeout(0)` 让出事件循环,否则同步连发 N 帧同样会把
ping/pong 与接收侧的解码压到这一轮循环之后。

连接不在 OPEN 状态时立即停止投递剩余帧:拆连后没人收,继续一帧帧走完全程只是白等
水位轮询(还会让重连后的新会话排在旧投递之后)。

批量期间 `bulkActive = true` 时,`sendRateLimited` 把**其他消息一律插到队首**:块响应、
增量索引、控制帧才是对端正等着的东西,一份大索引不该把它们压到后面。批量帧自己一次
只入队一帧,帧的编码也推迟到轮到它时再做,避免同时持有整份 JSON 的多份副本。

### 4. 探活增加「出站积压仍在减少」的例外

`startHeartbeat` 判死前多看一眼 `socket.bufferedAmount` 与上一轮心跳的差值
(`outboundDrainObserved`):缓冲在减少 = 链路忙但对端在读,不是死连接;缓冲不减
(只增不减,或原地不动)= 对端真的不读了,照常 `terminate()`。

这个判据能区分两者是有物理依据的:死连接上对端不消费,TCP 窗口填满后写缓冲**只增
不减**;忙链路的缓冲随对端消费持续下降。仅靠「这一轮有没有 pong」无法区分二者。

## 后果

- **实测条目数**:用新规则遍历当前工作区(排除硬忽略),活跃文件 588 个、
  目录 68 个,规则 85 行。改前同一目录的活跃索引条目是 106,863 条 —— 差三个数量级,
  全部来自 `rust/target` 与 `moonbit/_build`。MoonUI 同口径 351 个文件。
- **故障复现与验证**:`test/index-chunking.test.ts` 14 例钉住切片的字节上限、无损
  拼回、能力开关的两种行为、接收侧的重启/重复/畸形/按目录隔离,以及
  「真实 transport → 真实 dispatcher」的端到端一轮。
  `test/ignore.test.ts` 新增 6 例覆盖 rust/target + moonbit/_build + `.mooncakes`、
  任意深度的 `_build`、深层负向覆盖、被忽略目录内的 `.gitignore` 不读、
  `.syncxignore` 推翻嵌套规则。
  真实双 daemon 的 `test/integration/two-daemons.test.ts` 另有一条:共享根下
  `rust/.gitignore` 写 `/target`,对端收到 `rust/src/main.rs` 而**收不到**
  `rust/target/debug/app`;同一条用例把 `SYNCX_INDEX_CHUNK_BYTES` 压到 256B,
  让分片发送与拼装在真实 ws 链路上各跑一遍。关掉嵌套规则立刻红(已验证),
  关掉分片不会红 —— 单帧路径本来也能同步这份小索引,分片正确性由单测钉住。
- **不再需要 `.syncxignore` 兜底**:此前给这类工程临时止血的办法是在共享根写
  `.syncxignore` 列出 `rust/target/` 等;现在子目录的 `.gitignore` 自己就够了。
  已有 `.syncxignore` 不受影响。
- **索引库里的旧行不会自动消失**(与 ADR-0012 同一口径):规则只影响后续扫描与入向
  过滤。要彻底清掉,需在**两端**各做一次「移除共享目录(含索引库)」再重新添加,
  否则 `syncx status` 的「索引条目」仍会把旧行算在内。
- **升级顺序不敏感**:分片只在双方都宣告 `index-chunk1` 后发生;任一端是旧版就退回
  单帧。单帧超 64MB 的问题因而只在「双方都是新版但目录极大」时才可能重现 —— 而那时
  分片已经生效。**双侧都升级是这次修复生效的前提**,单独升级一端只能得到嵌套忽略
  带来的条目数下降,拿不到分片与探活例外。
- **每轮扫描多一次目录遍历。** 嵌套规则要现读(`.gitignore` 5 秒热加载的既有约定),
  `readNestedGitignoreLines` 因此每轮做一次「只 readdir、不 stat」的树遍历,与扫描器
  并列。对本项目 68 个目录可忽略;对被忽略子树则两边都因剪枝而变便宜(改前那 105k 条
  构建产物每轮都要 stat)。若将来出现十万级目录的共享根,再引入按 mtime 的规则缓存。
- **多一层内存持有**:拼装中的索引明文最多 256MB(正常 50MB 级目录约 1/5),
  集齐后一次性交给规划器。这与既有 `folder-index-snapshot` 的分片拼装同一取舍。
- **未处理**:`MAX_MESSAGE_BYTES` 仍是 64MB,没有改成「超限即报错」。分片把普通目录
  的帧压到 14MB 级之后,这个上限对索引不再是瓶颈;块响应本来就按块切。若将来出现
  单条目就超过一片的极端情况,`encodeIndexChunks` 仍会产出一个超预算的片 ——
  这一路径未加硬闸门,因为当前索引条目远达不到该量级。
